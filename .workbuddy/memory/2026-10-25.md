## 视图绑定 inflate 重载歧义修复（方法引用 → lambda）
- `MainActivity.kt:12` 与 `HomeFragment.kt:20` 原用 `XxxBinding::inflate` 方法引用，因生成的 Binding 类 `inflate` 被重载（1 参 + 3 参），Kotlin 方法引用无法靠参数个数消歧，报 `Overload resolution ambiguity`。
- 改法：统一改为显式 lambda，在 lambda 体内按参数个数调用，自动消歧：
  - MainActivity：`override val bindingInflater: (LayoutInflater) -> ActivityMainBinding = { inflater -> ActivityMainBinding.inflate(inflater) }`（补 `import android.view.LayoutInflater`）
  - HomeFragment：`override val bindingInflater: (LayoutInflater, ViewGroup?, Boolean) -> FragmentHomeBinding = { inflater, parent, attach -> FragmentHomeBinding.inflate(inflater, parent, attach) }`（补 `LayoutInflater`/`ViewGroup` 导入）
- 经验：今后任何继承 `BaseActivity`/`BaseFragment` 的页面，写 `bindingInflater` 都用 lambda，不要直接 `::inflate`。

## TitleBar tb_height "不生效" 排查
- 根因不是属性没读取，而是 `app:tb_height="96dp"` 被加在了 `activity_base.xml` 的 TitleBar 上，而该 TitleBar 被 `MainActivity.hideTitleBar()` 设为 GONE（隐藏）；Home 屏实际可见的是 `BaseFragment` 使用的 `fragment_base.xml` 里的 TitleBar（没有 tb_height，走默认 50dp）。属性本身读取正常，只是加错了实例。
- 修复：把 `app:tb_height="96dp"` 加到 `fragment_base.xml` 的 TitleBar（让可见的 Fragment 级标题栏生效，全局 96dp）。
- 另补齐运行时方法 `setTitleBarHeightDp/Px`（此前文档称 tb_height 无对应运行时方法，属缺口），并同步修正 `TitleBar.kt` 文档表。

## 简化 BaseListFragment 类型参数（去除冗余 Entity/Key）

## 新增 ExampleHttpRequest.kt 网络请求协程用法参考
- 位于 `app/src/main/java/com/example/androidpro/ExampleHttpRequest.kt`（主工程下，方便查看）。
- 整理两部分：OkHttp(SimpleHttp) 与 Retrofit 两套写法，覆盖 GET/POST-JSON/POST-form/PUT-JSON/DELETE/DELETE-JSON/upload/download 全部请求方式。
- 协程并发模式：多个独立请求用 `coroutineScope { async{}.awaitAll 变体（逐个 await 处理）}`；要求"任一失败不连坐"用 `supervisorScope`；关联请求（下一请求依赖上一返回）直接顺序写（同一协程天然串行）；另有"先并发再依赖"的混合示例。
- 关键点记录：SimpleHttp 统一返回 `ApiResult<T>` 不抛异常；Retrofit 默认返回裸类型、失败抛异常（用 `safeApi` 包成 ApiResult）；两者网络已在 IO 线程，调用方勿再 `withContext(Dispatchers.IO)`。`core:network` 以 `api` 暴露 okhttp/retrofit，`gson`/`converter-gson` 是 implementation，app 不可见（故 safeApi 不特判 SERIALIZATION）。
- 沙箱无 Android SDK，未编译验证；示例按真实签名编写，请本地 `./gradlew :app:compileDebugKotlin` 验收。
- 补充「六、并发 + 各自独立渲染（谁先回来谁先显示，互相不影响）」章节：与前文 `async+awaitAll` 的"等全部"范式区分，改用 `launch`（每请求一协程）+ 独立 `StateFlow`（每块一个）实现先到先渲染、互不阻塞；含 SimpleHttp 版（推荐，ApiResult 不抛异常天然隔离）与 Retrofit 版（每个 launch 须 try/catch，避免未捕获异常上报）。UI 端各自 `collect` 对应区块。
- 补充「七、网络请求与 Flow 结合」章节：用响应式 Flow 重写前几章场景 + Flow 独有杀手锏。
- 补充「八、带参数的 Flow 请求封装（参数可多可少）」章节：设计原则 = 底层万能 `requestFlow { }` lambda（任意参数组合）+ 带默认参数的便捷函数（getFlow/postJsonFlow/postFormFlow/putJsonFlow/deleteFlow，query/headers 默认空，命名实参少打字）+ 超多参数用 data class 承载 + `toQuery()` 转 Map（类型安全、可复用）+ 未覆盖组合回退 lambda 兜底；并演示参数化 Flow 与 zip/flatMapConcat 组合。文件顶部新增 `Item` 示例数据类。含 `requestFlow`/`getFlow`（把请求包成冷流 Flow，带 `flowOn(IO)`/`retry`/`catch` 兜底）、`zip`（并发等全部，对应第三章 awaitAll）、`combine`（并发谁先到谁触发下游，对应第六章整体版）、`flatMapConcat`（依赖请求串行传参，对应第四章）、`stateIn`+`map`（区块独立 StateFlow）、`debounce`+`flatMapLatest`（搜索防抖+自动取消旧请求）。真实函数 7.0-7.3 可编译；7.4/7.5 为 ViewModel 注释模板（依赖 lifecycle/viewModelScope）。
