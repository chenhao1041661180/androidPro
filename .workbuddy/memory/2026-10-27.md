## 网络层：统一 SimpleHttp 与 Retrofit 的返回格式为 ApiResult
需求：NetworkClient.http 返回 ApiResult<T>，NetworkClient.service（Retrofit）返回裸 T 且抛异常；希望两者统一为同一返回形态。

- 新增 `core/network/SafeApi.kt`：公共 `suspend inline fun <T> safeApi(crossinline block: suspend () -> T): ApiResult<T>`，把任意会抛异常的 suspend 调用（典型 Retrofit）包成 ApiResult，错误映射与 SimpleHttp 一致（HTTP/TIMEOUT/CONNECTION/IO/SERIALIZATION/UNKNOWN）。
- 关键修复：旧 `ExampleHttpRequest` 里的私有 `safeApi` 最后一个 `catch (e: Throwable)` 会**吞掉 CancellationException**，破坏“界面销毁→协程取消”保证；新版本首个 catch 就 `throw e` 原样上抛。
- 因 Gson 在 core:network 是 implementation，把 safeApi 放进 core:network 才能正确映射 SERIALIZATION（app 层做不到）。
- 删除 ExampleHttpRequest 中的私有重复 safeApi，改为 import 公共版本；同步更新头部说明（第 2、4 点）。
- 仍无法本地编译（沙箱无 Android SDK），需用户 `./gradlew :core:network:compileDebugKotlin` 与 `:app:compileDebugKotlin` 验收。

## 网络层：类型层面统一（Retrofit 接口直接返回 ApiResult<T>）
需求：让 Retrofit 接口方法直接声明 `suspend fun x(): ApiResult<T>`，免去 safeApi 包裹，与 SimpleHttp 在类型层面完全统一。

- 新增 `core/network/ApiResultCall.kt`：`ApiResultCall<T>` 实现 `Call<ApiResult<T>>`，把底层 `Call<T>` 的响应/异常统一成 ApiResult（HTTP/TIMEOUT/CONNECTION/IO/SERIALIZATION/UNKNOWN）。
- 新增 `core/network/ApiResultCallAdapterFactory.kt`：`CallAdapter.Factory`，识别 `ApiResult<T>` 返回类型并装配；非 ApiResult 类型返回 null 交给默认适配器，故“原始 Retrofit 用法”与“统一 ApiResult 用法”并存不破坏。
- 关键：Retrofit/OkHttp 取消时 onFailure 给的是 `IOException("Canceled")`，用 `delegate.isCanceled()` 识别并转成 `CancellationException` 上抛，保留“界面销毁→协程取消”保证。
- `NetworkClient.build()` 的 Retrofit.Builder 增加 `.addCallAdapterFactory(ApiResultCallAdapterFactory)`。
- `ExampleHttpRequest.kt` 新增 `UserApiUnified`（直接返回 ApiResult<T>）与 `retrofitUnified()` 示例；头部补充说明。
- 仍无法本地编译（沙箱无 Android SDK），需用户跑 `:core:network:compileDebugKotlin` 与 `:app:compileDebugKotlin` 验收，并跑一次真实接口+取消验证 CallAdapter 对 suspend 返回 ApiResult 是否如预期。

## 修复：启动时一次性连拉 4 页（page=1/2/3/4）
现象：进入 App 后 OkHttp 日志立刻连发 posts?_page=1/2/3/4。
根因：`ListRepository` 的 `PagingConfig` 没设 `initialLoadSize`，其默认值为 `pageSize * 3`（20*3=60）；而 RemoteMediator 的 REFRESH 只拉 1 页（20 条），Paging 为凑够 60 条会连续 APPEND 第 2、3 页，再叠加 `prefetchDistance=5` 拉到第 4 页 —— 与日志完全吻合。
修复（core/list/ListRepository.kt）：
```kotlin
PagingConfig(
    pageSize = pageSize,
    initialLoadSize = pageSize,   // 关键
    prefetchDistance = 3,
    enablePlaceholders = false,
)
```
已排除的因素：DB 是单例（DatabaseProvider），VM 只创建一次（by viewModels），Fragment 只 collect 一次。
预期：启动只发 1 个请求；滚动接近底部才加载下一页。
若仍复现，下一步排查：RecyclerView 在 collect 时高度为 0（布局未测量）导致 Paging 持续 append；可在 ListRemoteMediator.load 里临时打印 loadType+page 确认。

## 续：启动变成「两页每页两次共四次」
用户反馈改完 initialLoadSize 后变成 p1×2 + p2×2。查了 Paging3 源码（`PageFetcher` / `PageFetcherSnapshot`）：
- `PageFetcher.refreshChannel` 传的是 `triggerRemoteRefresh`；只有 `Adapter.refresh()`/初始化才传 true，
  **PagingSource 失效（Room 写库导致）传的是 false** —— 即失效重建出来的 generation **不会**再触发一次远程 REFRESH。
  所以「失效 → 重复 REFRESH」这条旧假设不成立。
- 真正的漏洞是 APPEND 的 **check-then-act 竞态**：`读 nextPage → 网络往返 → 写库`。网络往返期间 Room 写入甩出新 generation，
  新 generation 也走 APPEND 并读到同一个 nextPage，于是**同一页被并发请求两次**。

修复三处（均已 `./gradlew :core:list:compileDebugKotlin :app:compileDebugKotlin` 编译通过，JAVA_HOME 需指向 JDK 21，默认 java8 会导致 AGP 配置失败）：
1. `ListCache` 新增 `suspend fun <R> transaction(block)`；`BaseListCache` 第一个构造参数改为 `RoomDatabase`，
   用 `androidx.room.withTransaction` 实现。`PostCache` 与 `HomeFragment` 同步传入 `DatabaseProvider.database`。
   「清表 + 写数据 + 更新游标」合并成一次提交，失效次数 3→1。
2. `ListRemoteMediator` 拆成 `loadRefresh` / `loadAppend`；REFRESH 的写库进事务；**APPEND 加游标 CAS**：
   事务里二次比对 `nextPage()`，不等则丢弃本次结果返回 Success（数据已在本地），避免重复拉页。
3. mediator 里加了 `Log.d("RemoteMediator", ...)` 打印 loadType/page，用于确认是否只有一个 pipeline。

经验：调试 InvalidationTracker / generation churn 时，别想当然认为「失效=重复请求」，要先确认真源码里的 `triggerRemoteRefresh`。
gradle 编译必须带 `JAVA_HOME`（本机 /Library/Java/JavaVirtualMachines/jdk-21.jdk/Contents/Home）。

## 收尾定案：根本没有重复请求，是 OkHttp 日志一请求两行
用户贴的 mediator 日志只有两行：
```
D/RemoteMediator: load REFRESH page=1 size=20
D/RemoteMediator: load APPEND  page=2 size=20
```
即 load() 总共只被调用 2 次；`PostApi.loadPage` 里只有一次 `NetworkClient.http.get`，所以真实请求就是 2 个。

那为什么看起来「每页两次」？解压 `logging-interceptor-5.3.0-sources.jar` 看源码：
- 请求行：`"--> ${request.method} ${redactUrl(request.url)}..."`  含 URL
- 响应行：`append(" ${redactUrl(response.request.url)} (${tookMs}ms")`  **响应行也含 URL**

所以 Level.BASIC 下**一次请求打两行，两行都带同一个 URL**，看起来就像发了两次。
之前「两页各两次共四次」= 2 个请求 × 2 行 = 4 行，和 initialLoadSize 修复后的预期完全一致（修复前是 4 个不同页 × 2 行）。

验证方法：Logcat 过滤框只数 `--> ` 开头的行，或直接看 mediator 的 load 日志条数。
结论：initialLoadSize 那次修复是有效的；事务化 + 游标 CAS 属于正确性加固（原子性、并发重复写），不是本次"重复"的解药。
若要让日志一行一请求，可把 HttpLoggingInterceptor 换成自定义单行 logger（未做，等用户决定）。

## 答疑：为什么启动就拉了两页（不是重复，是 prefetch）
用户疑惑：进 App 应该只拉首页，为何立刻又拉第二页。
结论：这不是 bug、也不是重复（mediator 日志证明每页只 load 一次）。原因 = Paging 3 的 **prefetch**：
- 看 androidx `PageFetcherSnapshot.doInitialLoad`：首屏先按 `initialLoadSize` 拉一页；拉完后由 `HintHandler` 接收 presenter（RecyclerView）发来的 `ViewportHint`。
- 当 `enablePlaceholders = false` 时，Paging 无法用占位行填屏，必须靠真实数据填满视口 + `prefetchDistance` 余量。
- 若第一页 20 条没把"屏幕 + 3 条预取余量"撑爆（即已可视为"滚动到底"），Paging 立刻发 APPEND 拉下一页，保证不出现空白。
- 真机上 post 卡片很高，20 条远超一屏，通常就只请求 1 页；模拟器/矮列表则触发第 2 页。
想严格只拉首页的杠杆：① 调大 `initialLoadSize` 到 ≥ 屏幕+余量（脆弱）；② `enablePlaceholders = true`（需 Adapter 处理 null 占位项，复杂度高）。实践中建议保留：prefetch 是预期且健康的行为。
